# Token 消耗分析

> 实测口径：`/api/usage` 返回本进程累计用量。按调用目的分类。
> 价格表在 `autoalpha/llm.py:_PRICING`（美元/百万 token）。

## 一次完整运行的调用构成

| 阶段 | 调用次数 | 输入规模 | 说明 |
|---|---|---|---|
| 关键词提取 | 1 | 很小 | 研究方向 → arXiv 查询词 |
| **论文语义打分** | ⌈N/20⌉ | **大** | 每批 20 篇，含标题+400字摘要 |
| **论文中文概述** | ⌈N/10⌉ | **大** | 每批 10 篇，含标题+600字摘要 |
| 因子假设提取 | 每篇论文 1 次 | 中 | 标题+完整摘要 |
| 因子中文说明 | ⌈M/10⌉ | 中 | 每批 10 个因子 |
| **因子代码生成** | 每因子 1 次 | 中，**输出大** | 输出完整 Python，约 1-2k token |
| 代码修复 | 失败时每次 1 | 中 | 含错误栈，最多 2 次 |

N = 论文数（默认预取 200，过滤后展示 10），M = 因子假设数。

## 哪里最贵（实测，推翻了先验估计）

实测一次完整运行（中等模型，10 篇论文 → 3 个假设 → 2 个因子）：

| 用途 | 调用 | 输入 | 输出 | 成本 | 占比 |
|---|---|---|---|---|---|
| **score**（论文打分） | 10 | **22,884** | 440 | $0.0753 | **84.5%** |
| translate_paper（论文概述） | 1 | 1,770 | 1,943 | $0.0345 | 13.5% |
| codegen（代码生成） | 2 | 2,547 | 3,244 | $0.0563 | — |
| translate_factor（因子说明） | 1 | 794 | 832 | $0.0149 | — |
| extract（假设提取） | 1 | 546 | 1,213 | $0.0198 | — |
| keyword | 1 | 499 | 67 | $0.0025 | 2.1% |
| **合计** | **16** | **29,040** | **7,739** | **$0.2032** | |

**我原先以为代码生成最贵，实测是论文打分。** 原因：

`_PREFETCH=200` + `_FILTER_BATCH=20` → 为了展示 10 篇论文，
给 **200 篇全部打了分**，10 次调用吃掉 22.9k 输入 token。
而 arXiv 本身已按 relevance 排序，深尾部分几乎不可能进入最终展示。

→ 已加 `_SCORE_LIMIT = 60`（`paper_search_agent.py`）。**实测验证**：

| | score 调用 | score 输入 | 检索阶段成本 |
|---|---|---|---|
| 修复前 | 10 次 | 22,884 | $0.1122 |
| 修复后 | **3 次** | **7,004** | **$0.0544** |
| 变化 | −70% | −69% | **−52%** |

仍然正常找到并展示 10 篇论文，召回无感。需要更宽召回时调大该常量。

其余两点仍然成立：

- **输出 token 比输入贵 5 倍**（中等模型: $3 vs $15 /M），
  所以代码生成虽只 2 次调用，输出 3.2k token 就花了 $0.056。
- **重试是成倍放大器** —— 一次失败的代码生成等于白付一次输出成本。
  这就是 §A4 那个「空错误信息」bug 代价高的原因：
  3 次重试 = 3 倍代码生成成本，且全部无效。修复后 0 重试。

## 中文概述新增的成本

这次加的两个翻译调用，**设计上是批量的**：

```
10 篇论文 → 1 次调用（不是 10 次）
M 个因子  → ⌈M/10⌉ 次调用
```

单次翻译调用：输入约 10×600 = 6k token，输出约 10×120 = 1.2k token。
按 中等模型计价 ≈ `6k×$3/M + 1.2k×$15/M` ≈ **$0.036**。

因子说明更小：输入约 M×200，输出约 M×150。M=4 时 ≈ **$0.01**。

**实测：中文概述共 $0.0494**（论文 $0.0345 + 因子 $0.0149），
占单次运行总成本的 **24%**。

注意翻译的 **输出 token 偏高**（论文概述输出 1,943 > 输入 1,770），
因为中文概述本身就是要生成大段文字。这是它占比不低的原因。

如果嫌贵，把翻译切到小模型（约 1/3 单价）可降到约 1/3 ≈ $0.016 —— 
翻译对模型能力不敏感，这是性价比最高的降本点。

## 省钱的几个开关

| 做法 | 省多少 | 代价 |
|---|---|---|
| 翻译改用小模型 | 翻译成本 ↓ 2/3 | 几乎无感 |
| **降低 `_SCORE_LIMIT`** | **打分成本线性下降（已设 60，省 70%）** | 召回变窄 |
| 一次少选论文/因子 | 线性下降 | 产出变少 |
| 修好失败路径的错误信息 | **避免 2-3 倍无效重试** | 无 |
| 关掉 Judge（`factor_judge_agent`） | 每因子 1 次调用 | 失去语义审查 |
| P2：内层 GP + 外层 LLM | 预期降一个数量级 | 需实现 |

最后一项是根本解法：参数/结构的局部搜索交给遗传编程（零 LLM 调用），
LLM 只做诊断与协议级改进。见 `docs/OPTIMIZATION_PLAN_2026Q4.md` P2-2。

## 怎么查实际用量

```bash
curl -s http://127.0.0.1:8765/api/usage | python3 -m json.tool
```

页面上也有「Token 用量」卡片，每轮结束自动更新，含按用途的分解。

注意：计数是**本进程累计**，重启服务会清零。多次运行会累加。
